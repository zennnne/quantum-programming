รันจริงบน IBM QX แล้วปิดคอร์สครึ่งแรก

บท 0015 เดินโปรแกรมจนเห็นว่า payload ไปโผล่ที่ Bob ได้ เป๊ะ 100% — แต่นั่นคือบนกระดาษค่ะ · บทนี้เอาโปรแกรมเดียวกัน ไปรันบน QPU จริงของ IBM 1,024 รอบ แล้วอ่านผลว่ามันสำเร็จกี่เปอร์เซ็นต์ ปิดท้ายด้วยแผนที่ QPU primitives ที่บอกว่า Lec 05–09 จะพาไปไหนต่อ

บทนี้จับ 3 อย่าง
① โค้ดจริง (OpenQASM) ต่างจากวงจรในตำรายังไง — และทำไมถึงต้องต่าง
② อ่านกราฟผลการวัดเป็น + เข้าใจ post-selection ว่าทำไมต้องทิ้งผลทิ้งไป 6 ใน 8 กลุ่ม
③ QPU primitives 4 ขั้น = โครงของทุกแอปพลิเคชันควอนตัม และเป็นสารบัญของ Lec 05–09
ส่วนที่ 1 — เอาโปรแกรมลงเครื่องจริง

เครื่องที่ใช้: IBM 5-qubit QPU (ibmqx4)

สไลด์ย้ำว่า “วิธีเรียนที่ดีที่สุดคือลงมือทำ” — ตัวอย่างนี้ไม่ได้รันบน simulator แต่รันบน QPU จริงผ่านเว็บ IBM Q Experience กดปุ่มเดียวรันได้เลย (สไลด์ p3–p5)

แต่ QPU จริงมีข้อจำกัดที่ simulator ไม่มี: qubit ไม่ได้ต่อถึงกันทุกคู่ ผัง connectivity ของ ibmqx4 เป็นแบบนี้ค่ะ

เส้นเชื่อม = คู่ที่ทำ CNOT ให้กันได้ · q0 → q4 ไม่มีเส้นตรงถึงกัน
นี่แหละเหตุผลที่ตัวอย่างเลือก teleport จาก q[0] ไป q[4] — สองตัวนี้ คุยกันตรงๆ ไม่ได้เลย ต้องผ่าน q[2] ที่อยู่ตรงกลาง · หน้าที่ของ q[2] ในโปรแกรมนี้คือ ep (ครึ่งหนึ่งของคู่พัวพัน) พอดี → บทบาททั้งสามจึงเป็น q[0] = alice/payload · q[2] = ep · q[4] = bob

โค้ดจริง: OpenQASM

ภาษาที่ IBM ใช้เขียนวงจรคือ OpenQASM · หน้าตาเหมือนภาษาแอสเซมบลี — หนึ่งบรรทัด = หนึ่ง gate ตามด้วยชื่อ qubit (สไลด์ p6–p7)

include "qulib1.inc";
qreg q[5];              // qubit 5 ตัว
creg c[5];              // ที่เก็บผลวัด (บิตคลาสสิก) 5 บิต

// Step 1: Create an entangled pair
h  q[2];
cx q[2], q[4];
barrier q[0], q[1], q[2], q[3], q[4];

// Step 2: Prepare a payload
x  q[0];
h  q[0];
t  q[0];
barrier q[0], q[1], q[2], q[3], q[4];

// Step 3: Send
h  q[0];
h  q[2];
cx q[2], q[0];
h  q[2];
measure q[0] -> c[0];
measure q[2] -> c[2];
barrier q[3], q[4];

// Step 4: Receive
x  q[4];
z  q[4];
barrier q[3], q[4];

// Step 5: Verify
tdg q[4];
h   q[4];
x   q[4];
measure q[4] -> c[4];

วาดโค้ดนี้เป็นวงจร (สไตล์ QCEngine ที่ออกสอบ)

ตัดสาย q[1], q[3] ที่ไม่ได้ใช้ทิ้ง เหลือ 3 สายตามบทบาท จะได้หน้าตาแบบนี้

⚠️ จุดที่จะทำให้งง ถ้าไม่รู้ก่อน — โค้ดนี้ “ไม่เหมือน” วงจรในบท 0014/0015 ถึง 3 จุด
  1. Step 3 CNOT กลับทิศ — ตำราใช้ ep.cnot(alice) (alice คุม) แต่โค้ดเขียน cx q[2], q[0] (ep คุม) เพราะ ibmqx4 ต่อ CNOT ได้ทิศเดียว · ใช้เอกลักษณ์
    CNOT(a→b)  =  (H⊗H) · CNOT(b→a) · (H⊗H)
    แล้ว H ตัวท้ายบน alice ไปหักล้างกับ HAD ของ Step 3.2 ที่ต้องทำอยู่แล้วพอดี → เหลือ h q0; h q2; cx q2,q0; h q2 เป๊ะตามโค้ด
  2. prep payload เป็นคนละสูตร — วงจรในตำรา (บท 0015) ใช้ H–φ45–H แต่โค้ดนี้ใช้ x–h–t · ทั้งคู่ถูก แค่เตรียม payload คนละตัวกัน (ที่สำคัญคือ verify ต้องเป็นตัวย้อนของ prep เสมอ — ที่นี่คือ tdg–h–x) · สไลด์เอาสองเวอร์ชันมาปนกันในบทเดียว ถ้าเจอในข้อสอบให้ดูว่าโจทย์ยกวงจรหรือยกโค้ดมา
  3. ไม่มี if เลย — Step 4 เขียน x q[4]; z q[4]; ลอยๆ = Bob แก้ทุกรอบ ไม่ว่า Alice จะอ่านได้อะไร ← จุดนี้สำคัญมาก เก็บไว้ใช้ตอนอ่านผลค่ะ

ผลการรัน 1,024 รอบ

กด Run แล้ว IBM จะรันโปรแกรมซ้ำ 1,024 รอบ แล้วนับว่าแต่ละแบบออกมากี่ครั้ง (รันรอบเดียวบอกอะไรไม่ได้ เพราะผลการวัดเป็นการสุ่ม) (สไลด์ p17–p19)

วิธีอ่าน label (ข้อสอบชอบถาม) — เลข 5 บิตอ่าน ซ้าย → ขวา = c[0] c[1] c[2] c[3] c[4] (ไม่ใช่กลับด้านแบบเลขฐานสองปกติ!)
→ ตัวที่ 1 = c[0] = alice · ตัวที่ 3 = c[2] = ep · ตัวที่ 5 = c[4] = bob (บิต verify)
→ ตัวที่ 2 กับ 4 เป็น 0 เสมอ เพราะ q[1], q[3] ไม่ได้ใช้ → ใช้จริงแค่ 3 qubit จึงมี 2³ = 8 แท่ง
แท่ง 10001 หมายความว่ารอบนั้น Alice กับ Bob อ่านได้อะไร?
ถูกต้องค่ะ! หยิบตัวที่ 1, 3, 5 ออกมา → 10001 = alice 1, ep 0, bob 1 · ตัวที่ 2 กับ 4 เป็นที่ว่างของ q[1], q[3] ที่ไม่ได้ใช้
ยังไม่ใช่ค่ะ — อย่านับติดกัน ให้ข้ามตัวที่ 2 กับ 4 ทิ้ง เพราะเป็นช่องของ q[1], q[3] ที่ว่าง → เหลือตัวที่ 1, 3, 5 = alice, ep, bob

post-selection: ทำไมต้องทิ้งผล 6 แท่งจาก 8

ย้อนกลับไปที่จุดที่ 3 ของกล่องแดงเมื่อกี้: โค้ดนี้ไม่มี if Bob จึงทำ x แล้ว z (= NOT แล้ว PHASE 180°) ทุกรอบ · แต่กฎจากบท 0015 บอกว่า Bob ควรทำสองอย่างนี้เฉพาะตอนที่ Alice อ่านได้ 1 ทั้งคู่

→ รอบที่ Bob บังเอิญทำถูก = รอบที่ alice = 1 และ ep = 1 = label ที่ขึ้นต้นด้วย 1 0 1 · · เท่านั้น = 2 แท่งขวาสุด · อีก 6 แท่ง Bob แก้มั่วไปเรียบร้อยแล้ว → ทิ้ง
การ “เก็บเฉพาะรอบที่เงื่อนไขตรง แล้วทิ้งที่เหลือ” เรียกว่า post-selection (การคัดเลือกผลย้อนหลัง) (สไลด์ p44)

ในสองแท่งที่เหลือ ต่างกันแค่บิตสุดท้าย = ผล verify ของ Bob · จากบท 0015 รู้แล้วว่าถ้า teleport สำเร็จ verify ต้องได้ 0 เสมอ

① รอบที่ Bob แก้ถูกทั้งหมด = 194 + 27 = 221
② ในนั้น verify ได้ 0 (สำเร็จ) = 194 · ได้ 1 (ล้มเหลว) = 27
③ success rate = 194 ÷ 221 = 87.8%
ทำไม success rate ถึงเป็น 87.8% ไม่ใช่ 194 ÷ 1,024 = 19%?
ใช่เลยค่ะ! 803 รอบนั้นไม่ได้แปลว่า teleportation พัง — แค่โค้ดไม่มี if Bob เลยแก้ไม่ตรงกับที่ Alice อ่านได้ ถ้ามี if จริงๆ รอบพวกนั้นก็จะสำเร็จด้วย → ต้องตัดออกจากตัวหาร
ยังไม่ใช่ค่ะ — เครื่องวัดครบทุกรอบ และ Alice ไม่มีทาง “อ่านผิด” (ผลของ Alice สุ่มถูกต้องเสมอ) · ปัญหาอยู่ที่ฝั่ง Bob: ไม่มี if เลยแก้แบบเดียวทุกรอบ → ใช้ได้แค่รอบที่บังเอิญตรง
ข้อจำกัดของ verify ที่ต้องรู้ (สไลด์ p46) — ถ้า qubit ที่ Bob ได้เพี้ยนไปนิดเดียว (เกือบเหมือนของ Alice) การ verify มีแนวโน้มจะรายงานว่า “สำเร็จ” อยู่ดี · เพราะ READ ครั้งเดียวบอกสถานะไม่ได้ → ต้องรันหลายรอบเท่านั้นถึงจะเชื่อตัวเลขได้ · 87.8% ในปี 2019 ถือว่าไม่แย่สำหรับเครื่องที่ดีที่สุดในยุคนั้น แต่ก็ยังไม่ควรฝากของสำคัญไว้ค่ะ

เกร็ดปิดท้าย Lec 04 — The Fly (สไลด์ p48–p49, ไม่ใช่เนื้อหาสอบ) อาจารย์ยกหนัง The Fly (ต้นฉบับ 1958 · เวอร์ชัน Jeff Goldblum 1986) ที่พระเอก teleport ตัวเองโดยไม่รู้ว่ามีแมลงวันอยู่ในห้องด้วย → ออกมาเป็นตัวประหลาด · ตำรามีโค้ดตัวอย่างที่ teleport “ภาพควอนตัมของแมลงวัน” (ผัง circle notation ~16×16 วง) โดยจงใจใส่ error ตามพล็อตหนัง รันออนไลน์ได้ที่ oreilly-qc.github.io?p=4-2 · ประเด็นจริงจังที่ซ่อนอยู่: teleportation ที่มี error นิดเดียวก็ให้ผลลัพธ์ที่ผิดไปเลย — ตรงกับข้อจำกัดของ verify ที่เพิ่งคุยกันค่ะ

QPU primitives — แผนที่ของทั้งคอร์ส

ถึงตรงนี้เรารู้จัก qubit ระดับพื้นฐานครบแล้ว (superposition, phase, entanglement, READ) สไลด์จึงเปิดชั้นถัดไป: QPU primitives = กล่องเครื่องมือระดับสูงที่เอามาประกอบเป็น แอปพลิเคชันจริง (สไลด์ p50–p51)

ทุกแอปพลิเคชัน QPU มีโครงเดียวกัน 4 ขั้น:

create superposition  →  compute in superposition  ⇅  phase manipulation  →  readout
① create superposition — เอา qubit เข้าสู่ superposition (HAD คือตัวแทน) เพื่อให้มี “หลายคำตอบพร้อมกัน” ให้คำนวณ
② compute in superposition — คำนวณกับทุกความเป็นไปได้พร้อมกัน ด้วยความขนานโดยปริยายของ superposition
③ phase manipulation — จัดการเฟสเพื่อให้คำตอบที่ต้องการ โผล่ออกมาตอน READ · ขั้น ② กับ ③ มักวนสลับกันหลายรอบ (ลูกศรสองหัว)
④ readout — READ ออกมาเป็นบิตคลาสสิก · ขั้นนี้เองที่ทำให้ทุกอย่าง ก่อนหน้า “มีความหมาย” หรือ “สูญเปล่า”
ทำไมขั้น ③ ถึงมีอยู่ — จากบท 0003 เรารู้ว่า READ มองไม่เห็นเฟสโดยตรง · phase manipulation คือการแปลง “ข้อมูลที่ซ่อนอยู่ในเฟส” ให้กลายเป็น “ขนาดของวง” ที่ READ เห็นได้ · ไม่มีขั้นนี้ = คำนวณเสร็จแล้วอ่านผลไม่ได้

ถ้าอัลกอริทึมหนึ่ง “คำนวณครบทุกคำตอบพร้อมกันแล้ว แต่ READ ออกมาได้แต่ค่าสุ่ม” แปลว่าขาดขั้นไหนไป?
ถูกต้องค่ะ! นี่คือเหตุผลที่มีขั้น ③ อยู่บนโลก — superposition อย่างเดียวไม่ช่วยอะไร เพราะ READ จะสุ่มหยิบมาแค่หนึ่งคำตอบ · ต้องใช้ phase manipulation (Lec 06–08) ดันคำตอบที่ต้องการให้วงใหญ่ขึ้นก่อน
ลองใหม่นะคะ — โจทย์บอกว่า “คำนวณครบแล้ว” (ผ่าน ① กับ ②) และ “READ ออกมาได้” (มี ④) · สิ่งที่หายไปคือขั้นที่ทำให้ผล READ ไม่สุ่ม
