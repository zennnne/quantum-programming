QSS lookup table: แปลค่า READ เป็นความสว่าง

บท 0044 จบที่ว่า QSS รัน AA + QFT แล้ว READ counter ออกมาได้ตัวเลขตัวหนึ่ง · แต่ตัวเลขนั้นยังไม่ใช่จำนวน subpixel ขาวตรงๆ · บทนี้คือชิ้นสุดท้ายของจิ๊กซอว์: ตารางที่แปลค่า READ กลับเป็นความสว่าง แล้วดูว่าตารางเดียวกันนี้ยังเอาไปทำอะไรต่อได้อีก

ทำไมต้องเรียนบทนี้: จับหลัก 4 อย่าง ① QSS lookup table (ตารางเทียบค่า): แถว = ค่า READ · คอลัมน์ = จำนวน subpixel ขาว · สว่าง = น่าจะเป็น ② ตารางนี้ไม่ขึ้นกับภาพ สร้างครั้งเดียวใช้ซ้ำ และเป็น fingerprint (ลายนิ้วมือ) ของขนาด tile + counter ③ แถวไหนสว่างช่องเดียว = มั่นใจ · แถวไหนกระจาย = ไม่มั่นใจ → ได้ confidence map (แผนที่ความมั่นใจ) ④ อยากได้สี → ใช้ bitplanes (ระนาบบิต) render ภาพขาวดำทีละ channel แล้วรวม
ของเก่าที่จะกลับมาใช้: DFT ของคลื่นจริงได้ peak คู่สะท้อน และถ้าความถี่ไม่ลงช่องพอดีจะรั่วไปช่องข้างๆ (บท 0028) · tile โดน flip M ตัว → AA แกว่งเร็วช้าตาม M → QFT อ่านความถี่ (บท 0044)

ส่วนที่ 1 · ตารางคืออะไร อ่านยังไง สร้างยังไง (p41–47)

ทำไมต้องมีตาราง (p41)

สไลด์บอกว่าเลขที่ READ ได้ "เกี่ยวข้องกับ แต่ไม่เท่ากับ" จำนวน subpixel ขาวใน tile · เหตุผลมี 2 ชั้นที่เราเห็นแล้วในบท 0044:

  1. ความถี่ของการแกว่งส่วนใหญ่ไม่ลงช่องพอดี → QFT ให้ peak ที่เบลอ กระจายไปหลายช่อง → READ ได้ค่าสุ่ม
  2. เลขช่องที่ออกมาถูกสลับลำดับอีกชั้นในโค้ดจริงของ QCEngine → ค่า READ ไม่เรียงตามจำนวน subpixel

ทางแก้ที่สไลด์ใช้คือไม่ต้องหาสูตรกลับ แต่ทำตารางไว้ล่วงหน้าเลยว่า "ถ้าขาว M ตัว จะ READ ได้อะไรด้วยโอกาสเท่าไร" แล้วเปิดตารางย้อนกลับ · คล้ายตารางแปลงหน่วยที่แปะข้างตู้เย็น: ไม่ต้องคิดสูตรทุกครั้ง แค่เปิดดู

Figure 11-14: หน้าตาของตาราง (p42–43)

ตัวอย่างของสไลด์ใช้ tile 4×4 (16 subpixel) + counter 4 qubit · อ่านแบบนี้:

  • แถว (แนวตั้ง) = ค่าที่ READ ได้ · counter 4 qubit → 2⁴ = 16 แถว (0–15)
  • คอลัมน์ (แนวนอน) = จำนวน subpixel ขาวที่เป็นไปได้ · 0 ถึง 16 → 17 คอลัมน์ (0 = ดำ · 8 = เทา · 16 = ขาว)
  • ความสว่างของช่อง = ความน่าจะเป็น · ยิ่งสว่าง ยิ่งน่าจะ · พื้นดำ = แทบเป็นไปไม่ได้
① ตัวอย่างในสไลด์ (p43): READ ได้ 10 → ไปดูแถว 10
② ช่องสว่างสุดอยู่คอลัมน์ 5 → เดาว่า tile นี้มี subpixel ขาว 5 ตัว
③ แต่ 4 กับ 6 ก็ยังสว่างพอควร และ 3 กับ 7 จางๆ → เป็นไปได้เหมือนกัน
④ นี่คือที่มาของ error: ค่า READ ค่าเดียวชี้จำนวน subpixel ได้ไม่เด็ดขาดเสมอไป

ลายของตารางบอกอะไร (คาโฮะอธิบายเสริม · สไลด์ไม่ได้พูด)

ลองสังเกตตารางด้านบนดี มีของแปลกอยู่ 2 อย่าง และทั้งคู่อธิบายได้ด้วยเรื่อง DFT ที่เรียนไปแล้ว:

แถวมาเป็นคู่หน้าตาเหมือนกัน
(2,3) (5,6) (4,7) (10,13) (11,12) (9,14) (8,15) · เพราะคลื่นจริงหนึ่งลูกให้ peak คู่สะท้อนเสมอ (เหมือน 8 กับ 248 ใน บท 0028) · พอโดนสลับลำดับช่อง peak คู่นั้นก็ไปตกแถวเลขคู่กันพอดี
คอลัมน์ 0 กับ 16 คมช่องเดียว
ขาว 16 ตัว = ไม่แกว่งเลย (ความถี่ 0) · ขาว 0 ตัว = กลับเครื่องหมายทุกรอบ (ความถี่ครึ่งหนึ่งพอดี) · ทั้งสองค่าลงช่องพอดี จึงไม่รั่ว · ค่าอื่นลงระหว่างช่อง จึงรั่วเป็นแถบ 3–5 ช่อง
ลองอ่านจากตารางเอง (ยังไม่ต้องคลิก): ถ้า READ ได้ 4 ควรตอบว่า tile นี้มี subpixel ขาวกี่ตัว
ใช่ค่ะ แถว 4 สว่างสุดที่ 14 · รองลงมา 13 · จางที่ 12 กับ 15 · สังเกตว่า READ 4 กลับแปลว่าเกือบขาวทั้ง tile — นี่แหละ "เกี่ยวแต่ไม่เท่า" (คลิกแถว 4 ในตารางเพื่อดูเปอร์เซ็นต์ได้)
ลองใหม่นะคะ ค่า READ ไม่ใช่จำนวน subpixel · ต้องไล่แถว 4 ไปทางขวาจนเจอช่องที่สว่างที่สุด แล้วอ่านเลขคอลัมน์ใต้ช่องนั้น

สร้างตารางยังไง: Example 11-5 (p44–45)

จุดสำคัญที่สุด: ตารางไม่ขึ้นกับภาพ (พูดให้ตรงคือ ไม่ขึ้นกับ quantum pixel shader) · เพราะ QSS นับแค่ว่า มีขาวกี่ตัว ไม่สนว่าขาวตัวไหน · ดังนั้นแค่จำลองว่า "flip M ตัวใดก็ได้" ทีละ M ก็ได้ตารางครบ · สร้างครั้งเดียว reuse ได้กับทุกงาน QSS ที่ tile กับ counter ขนาดเท่ากัน (p41, p44)

// Building a QSS lookup table                       ← สไลด์พิมพ์ # (JS ต้องเป็น //)
function create_table_column(color, qxy, qcount) {   // เรียก 1 ครั้ง = สร้าง 1 คอลัมน์
    var true_count = color;                          // คอลัมน์นี้ = ขาว color ตัว
    // Put everything into superposition
    qc.write(0);
    qcount.hadamard();                               // counter = ทุกจำนวนรอบพร้อมกัน
    qxy.hadamard();                                  // ผ้าใบเปล่าของ tile
    for (var i = 0; i < num_counter_bits; ++i) {
        var reps = 1 << i;                           // bit i ของ counter = 2ⁱ รอบ
        var condition = qcount.bits(reps);
        var mask_with_condition = qxy.bits().or(condition);
        for (var j = 0; j < reps; ++j) {             // ← สไลด์พิมพ์ติดกัน "for(varj=0;…"
            flip_n_terms(qxy, true_count, condition);         // แทน shader: flip M ตัวไหนก็ได้
            grover_iteration(qxy.bits(), mask_with_condition); // mirror
        }
    }
    invQFT(qcount);
    // Construct the lookup table
    for (var i = 0; i < (1 << num_counter_bits); ++i)
        qss_lookup_table[color][i] = qcount.peekProbability(i);  // แอบดูโอกาสของทุกค่า READ
}

โครงเหมือน qss_tile() ในบท 0044 ทุกอย่าง ต่างแค่ตัวเดียว: ที่ตรงเรียก pixel shader วาดรูป ถูกแทนด้วย flip_n_terms(qxy, true_count, …) ที่ flip แค่ "M ตัวไหนก็ได้" · และตอนจบไม่ READ แต่ใช้ peekProbability แอบดูความน่าจะเป็นของทุกค่า (ทำได้เพราะรันบน simulator — คาโฮะเสริม)

สไลด์พิมพ์ผิดในโค้ด (p44–45): บรรทัดแรกใช้ # เป็น comment (JavaScript ต้องเป็น //) · for(varj=0;j<reps;++j) พิมพ์ติดกัน · หนูแก้ให้รันได้แล้วในกล่องด้านบน

ตารางเป็น "ลายนิ้วมือ" ของอัลกอริทึม (p45–47)

หน้าตาของตารางบอกทันทีว่า QSS ที่ตั้งค่าแบบนี้เก่งแค่ไหน · สไลด์จึงเรียกมันว่า fingerprint · มีปุ่มปรับ 2 ตัว และแต่ละตัวยืดตารางคนละทิศ:

Figure 11-15 (คำนวณใหม่): counter 4 qubit เท่ากัน (16 แถว) · เพิ่ม subpixel = เพิ่มคอลัมน์

Figure 11-16 (คำนวณใหม่): tile 4×4 เท่ากัน (17 คอลัมน์) · เพิ่ม counter = เพิ่มแถว

คอลัมน์ = จำนวน subpixel + 1   ·   แถว = 2จำนวน counter qubit

อ่านลายนิ้วมือยังไง: จุดสว่างยิ่งแคบและแยกกัน = ค่า READ ค่าหนึ่งชี้จำนวน subpixel ได้เจาะจง (ดี) · จุดสว่างยิ่งยืดเป็นแถบยาว = ค่า READ ค่าหนึ่งครอบคลุมหลายจำนวน (กำกวม) · ดูจากรูป: tile ใหญ่ขึ้นแต่ counter เท่าเดิม → แถบยืด · counter มากขึ้น → จุดคมขึ้น (สอดคล้องกับ trade-off ในบท 0044: counter มาก = ภาพดี แต่รันโค้ดวาดรูปมากขึ้น)

สไลด์ขัดกันเอง (p47): หัวรูป Figure 11-16 เขียน "4x4 tile, 16 columns" แต่ Figure 11-15 ในหน้าเดียวกันเขียน "4x4 tile, 17 columns" · ที่ถูกคือ 17 เพราะขาวได้ 0–16 = 17 ค่า · ถ้าข้อสอบถาม ให้ตอบ 17 พร้อมเหตุผลนี้ได้เลย (ผิดมาจากรูปต้นฉบับในหนังสือ)
ลองคำนวณเอง: QSS ที่ใช้ tile 8×8 กับ counter 5 qubit จะได้ lookup table ขนาดเท่าไร
ถูกค่ะ แถว = 2⁵ = 32 (ค่า READ ที่เป็นไปได้) · คอลัมน์ = 64 + 1 = 65 (ขาวได้ 0 ถึง 64)
เกือบแล้วค่ะ แถวมาจากcounter (2⁵ = 32) · คอลัมน์มาจากsubpixel และต้อง +1 เพราะนับขาว 0 ตัวด้วย → 65

เพิ่มสีด้วย bitplanes (p50–52)

ภาพทั้งหมดที่ผ่านมาเป็น one-bit monochrome (ขาวดำ 1 บิตต่อ pixel): flip = ขาว · ไม่ flip = ดำ · ถ้าอยากได้สีมีสองทาง:

❌ ยัดหลายระดับลง phase/amplitude ตรงๆ
ใช้ไม่ได้ เพราะ Quantum Sum Estimation นับว่าถูก flip หรือไม่ (ใช่/ไม่ใช่) · ถ้า phase มีหลายระดับ กลไกนับจะพังทันที (p50)
✅ bitplanes (ยืมจากการ์ดจอยุคแรก)
ให้ pixel shader render ภาพขาวดำหลายภาพแยกกัน แต่ละภาพ = 1 บิตของภาพสุดท้าย · แต่ละภาพยังเป็น flip/ไม่ flip เหมือนเดิม QSS จึงใช้ได้ (p50)

ตัวอย่างของสไลด์ (p51): แยกเป็น 3 ภาพ R · G · B → supersample แต่ละภาพแยกกัน → รวมกลับเป็นภาพสี

① ถ้าไม่ supersample: แต่ละ channel เปิด/ปิดได้อย่างเดียว → 2 × 2 × 2 = 8 สี (รวมดำและขาว):
② พอ supersample: แต่ละ channel ได้หลายระดับเทา (ผสม subpixel ใน tile) → รวมแล้วเทียบเท่า 12-bit-per-pixel

💡 สไลด์ไม่ได้บอกว่าเลข 12 มาจากไหน · คาโฮะเดาว่า = 3 channel × 4 บิต (tile 4×4 ให้ราว 16 ระดับต่อ channel ≈ 4 บิต) · ตอนสอบให้จำแค่ "8 สี → เทียบเท่า 12-bit" ตามสไลด์

Figure 11-18 (p52, caption “Space Harrier eat your heart out!”): แถวบนเป็นภาพเทา 3 ภาพในกรอบแดง เขียว น้ำเงิน มีลูกศรชี้ลงไปรวมเป็นภาพสีภาพเดียว เป็นฉากดวงอาทิตย์เหนือขอบฟ้ากับพื้นลายตารางหมากรุก · สังเกตว่าแต่ละ plane มีหลายระดับเทา ภาพรวมจึงไล่เฉดได้ ไม่ได้ติดอยู่แค่ 8 สี · โค้ดเต็มที่ oreilly-qc.github.io/?p=11-6

ถ้าใช้ 4 bitplanes (ยังไม่ supersample) จะได้กี่สี
ถูกค่ะ แต่ละ plane = 1 บิต → 2⁴ = 16 สี · หลักเดียวกับ 3 plane → 2³ = 8
ลองใหม่ค่ะ 1 plane = 1 บิต (2 ทาง) · 4 plane = 2 × 2 × 2 × 2

สรุปคาบ Lec 11 (p53–54)

สไลด์สรุป 4 ข้อ (p53):

  1. ลองผสม QPU primitive แบบใหม่ๆ + domain knowledge นิดหน่อย อาจได้ QPU application ใหม่ (QSS = arithmetic + AA + QFT + ความรู้ด้านกราฟิก)
  2. ความสามารถในการ redistribute sampling noise (จัดการกระจาย noise ใหม่) แสดงให้เห็นว่า บางทีต้องมองข้าม speedup ถึงจะเห็นข้อดีของ QPU
  3. การกระจาย noise แบบใหม่นี้อาจมีประโยชน์นอกเหนือ computer graphics
  4. งานอื่นที่ใช้ Monte Carlo sampling หนัก: artificial intelligence · computational fluid dynamics · finance

p54: คาบนี้แทนภาพด้วย phase encoding แต่วงการ Quantum Image Processing ยังมี representation อื่นอีก (สไลด์ให้แค่ชื่อ): Qubit Lattice · FRQI (Flexible Representation of Quantum Images) · NEQR (Novel Enhanced Quantum Representation) · GQIR (Generalized Quantum Image Representation) · ซึ่งถูกเอาไปลองกับงาน template matching · edge detection · image classification · image translation

เรื่องสอบ: ครึ่งหลังของคาบนี้ไม่มีวงจรใหม่ (cheat sheet ไม่ต้องเติม) · ที่น่าออกคือ: อ่าน lookup table (READ → จำนวน) · ขนาดตาราง (แถว = 2counter, คอลัมน์ = subpixel + 1) · ทำไมตารางไม่ขึ้นกับภาพ · READ 0/1 มั่นใจ vs 2/3/4 ไม่มั่นใจ · bitplanes 3 plane = 8 สี → 12-bit

ทบทวนจากความจำ

ทำไมค่า READ ถึงใช้เป็นความสว่างตรงๆ ไม่ได้ peak ของ QFT เบลอ (ความถี่ไม่ลงช่อง) + ลำดับช่องถูกสลับ → ค่า READ "เกี่ยวแต่ไม่เท่า" จำนวน subpixel ขาว (p41)
แถว / คอลัมน์ / ความสว่าง ของ lookup table หมายถึงอะไร แถว = ค่า READ · คอลัมน์ = จำนวน subpixel ขาว · สว่าง = ความน่าจะเป็น · READ 10 → 5 (รอง 4/6, จาง 3/7) (p42–43)
ทำไมสร้างตารางครั้งเดียวแล้วใช้กับภาพไหนก็ได้ QSS นับแค่ "กี่ตัว" ไม่สน "ตัวไหน" → ใช้ flip_n_terms แทน shader ได้ · ใช้ซ้ำได้ถ้า tile + counter ขนาดเท่าเดิม (p41, p44)
เพิ่ม subpixel / เพิ่ม counter ตารางเปลี่ยนยังไง เพิ่ม subpixel = เพิ่มคอลัมน์ (แถบยืด กำกวมขึ้น) · เพิ่ม counter = เพิ่มแถว (จุดคมขึ้น) · 16 vs 17 columns → ที่ถูกคือ 17 (p45–47)
confidence map คืออะไร สว่างแปลว่าอะไร เปิดแถวของค่า READ ดูว่าคำตอบกระจายแค่ไหน ทำทุก pixel · สว่าง = น่าจะถูก · READ 0/1 มั่นใจ · 2/3/4 ไม่มั่นใจ (p48–49)
ทำไมต้อง bitplanes และ 3 plane ได้กี่สี ยัดหลายระดับลง phase แล้ว Sum Estimation พัง · render ขาวดำแยกทีละ channel · 3 plane = 8 สี → supersample แล้วเทียบเท่า 12-bit (p50–51)
